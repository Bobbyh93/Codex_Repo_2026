# Code Shift design and scope

Reference: concept.png. Desktop sidebar 200px, white content surface, navy #102139, teal #008d91, borders #e2e8ee, pale gray #f4f7f9. System sans typography, 32px page title, 24px patient heading, 14px body, 12px labels. Restrained 8px corners. Chart / timeline / setup navigation; patient and SBAR left, session roster and observation right. Mobile collapses to one column with horizontal navigation. Native SVG icons and code-native controls; no runtime remote assets.

## Checkpoint 2 (2026-10-14): scenario loaded

The engineering fixture is replaced by `server/scenario.js`: the N115C CAD / Chest Pain simulation scenario (Carl Shapiro, fictional educational patient) transcribed from the faculty instructor packet. Student-facing chart: patient banner (MRN, age, sex, DOB, allergies, code status, location, weight/height), SBAR, Overview (admission, PMH, HPI, social history), Labs (CBC, BMP, cardiac/coag with reference ranges), Orders (standing, medication, STAT, heparin protocol). The `facilitator` block (set-up, pre-SIM discussion, results to release, hypotension and heparin-titration guidance, student group assignments, observation checklist) is stripped on the server for student actors and rendered in an instructor-only Facilitator tab; API and browser tests assert students never receive it. Chest-Pain-(MI).docx (Maryland NGN test-bank item, different patient) was not used. No vitals are shown because the packet provides none. Existing sessions keep scenario_id `engineering-v1` in SQLite; the chart renders the current scenario regardless.

## Checkpoint 3 (2026-10-14): patient monitor

Instructor-controlled bedside monitor, Laerdal-style. `POST /api/vitals` (instructor only) stores HR, RR, SpO2, NIBP, temperature, rhythm, monitor on/off, and an optional trend time; the row also stores the "from" values captured server-side so every client interpolates the same trend. Rows are append-only (`vitals` table, user_version 2) and each change writes a public VITALS_SET evidence entry. Students get a "Document vitals" action (VITALS_RECORDED): the server composes the text from the values currently displayed, ignores any client text, and links the entry to the instructor's monitor change. Monitor page shows synthesized ECG and pleth traces (illustrative, not physiologic), colored readouts with alarm highlighting, and a wall-display fullscreen mode. Scenario presets live in the instructor-only facilitator block; the packet gives rhythm and lab events but no numeric vitals, so preset numbers are suggested teaching values for faculty to confirm. Clock skew between phones and the Pi is handled with a server-time offset. Tests cover role enforcement, validation, idempotent retry, trend capture, monitor-off behavior, forged-text rejection, and student visibility; the browser test applies a preset as instructor and verifies a student sees it and can document it.


## Checkpoint 4 (2026-10-14): eMAR with barcode verification, room display, provider messaging

eMAR: scenario medications (standing, STAT, PRN, and sim-day "assignable" orders chosen at session setup or toggled by the instructor; each toggle is a MED_ORDER_CHANGED entry). POST /api/meds records given / held / refused; a given with a wristband or label mismatch is stored as **blocked** with the reason and surfaces in the eMAR and timeline (debrief evidence). Verification is recorded as camera or manual as reported by the client; the app cannot prove a camera was used, which the UI states. Hold rules are checked against the live monitor SBP and flagged in the entry text, not enforced. med_events is append-only. Scanner: @zxing/browser (Code 128 + QR) in a modal; requires a secure context, so the installer generates a CA-flagged self-signed certificate and the server runs TLS when TLS_CERT/TLS_KEY are set, with an http helper on 8080 for redirect and certificate download. Labels: /labels renders Code 128 via jsbarcode for print. Room display: /display is a no-login kiosk page fed by the public read-only /api/display (vitals only); deploy/install-display.sh runs Chromium under cage on the Pi's HDMI output. Students no longer have a monitor page; the chart shows "Monitor now" with a Document vitals button. Provider messaging: PROVIDER_MESSAGE (students) and PROVIDER_REPLY (instructor only, must reference a message) on the existing entries API; a minimal Provider page. AI-assisted provider replies are deferred to a connected-device "premium" station per the platform's AI boundary.


## Checkpoint 5 (2026-10-14): scan-first enforcement and physical barcodes

Faculty constraint: physical scannable labels/meds are used so students build the real BCMA habit. Changes: sessions have scan_required (default on; instructor toggle via POST /api/session-settings, logged as SESSION_SETTING_CHANGED). With scanning required the server rejects any 'given' whose verification is not camera; with it off, manual entry needs a reason and the entry text reads "MANUAL ENTRY (reason)". Codes are normalized (trim, uppercase, no whitespace). The client sends the time of each scan; the server stores patient_scanned_at, med_scanned_at and scan_order on med_events and writes "wristband then label, N s apart" or "SEQUENCE: medication scanned before patient" into the entry. Students never receive barcode values (scenario and MAR rows are stripped server-side); the Give dialog therefore shows what was read, not whether it matches, and the server decides. Physical barcodes: barcode_aliases table (configuration, mutable; registration and removal are logged as BARCODE_REGISTERED). POST /api/barcodes (instructor) maps a code to the wristband or a medication; GET /api/barcodes/lookup previews what a code resolves to; scenario-printed codes cannot be re-assigned. resolveCode() checks scenario codes (barcode or barcodes[] per medication) then active aliases. UI: scan-first Give dialog (camera opens at step 1, auto-advances to step 2, confirm step shows both reads with Rescan), manual entry only when the session allows it, Scanning policy toggle and Physical barcodes registry on the instructor's eMAR, "Scanned out of order" and "N manual" markers on eMAR rows. Scanner adds vibration/beep on read, torch toggle, and more symbologies (Code 39, UPC/EAN, Data Matrix, ITF). Camera-path tests remain a hardware step (7c, 7c2, 7c3); headless tests cover the manual path, scan-required gating, registration, and the no-leak guarantee.


## Checkpoint 6 (2026-10-14): immediate scan verification, alerts before the decision, structured med evidence

From the BCMA fidelity audit (four lenses, adversarially verified): four findings stood after the scan-first rebuild and are addressed here. (1) Each read is verified the moment it happens: POST /api/meds/scan resolves the code, records a med_scans row (append-only: attempt, kind, code, symbology, camera/manual, matched, what it resolved to, time) and, on a mismatch, writes a public MED_SCAN_MISMATCH entry and returns the alert; the dialog shows a red "Stop" banner with vibration and offers Rescan, so the wrong item is caught before the medication step, as at a real bedside. Wrong vs unrecognized is distinguished (WRONG PATIENT / UNRECOGNIZED WRISTBAND / WRONG MEDICATION / UNRECOGNIZED LABEL). (2) Held and refused also start with the wristband scan when scanning is required; patient_match is stored and the entry says "patient identified by wristband scan". (3) Alerts are evaluated server-side before documentation from structured scenario timing (once, intervalMin, prn.minIntervalMin / maxDoses / windowMin) and the live monitor hold rule: ALREADY_GIVEN, TOO_EARLY, MAX_DOSES, HOLD_RULE. They appear on the eMAR row and at the top of the Give dialog; a give with open alerts is refused (409) unless the student acknowledges and gives a reason, which is written as "ALERTS OVERRIDDEN (reason): ..." and stored in alerts/override_reason on med_events; "Hold instead" pre-fills the hold reason. (4) The instructor snapshot and the evidence export (format v2) carry med_events and med_scans as structured rows for debrief and research. Findings the skeptics refuted as already built: manual entry as default, no scan sequencing, codes exposed to students, single hard-coded barcode per med, Code 128/QR only, case-sensitive matching, no haptic feedback, no torch. Deferred (after pilot): med-pass session context so one wristband scan covers several meds, per-field symbology in evidence, PRN indication capture, due-time lateness on the event, an explicit two-identifier attestation tap, GS1 application-identifier parsing.


Checkpoint 6 follow-up (audit plan steps 1-5): the scanner ignores a re-read of the item just scanned (no spurious wrong-medication alert while the phone is still on the wristband); server 409 alerts are carried straight into the dialog acknowledge block; labels get Code 128 quiet zones (20 modules each side), natural width, cut instructions, registered-package notes and an instructor gate; hold-rule wording now also states not met (with SBP) or not evaluated (monitor off / no vitals), and every medication entry links the monitor entry it was judged against; viewfinder fills a square with a reticle, torch only when the camera has one, patient identifiers shown large at step 1. Deferred: PRN indication capture (plan step 6).


Checkpoint 7 (2026-10-14): PRN/STAT indication is required at documentation (indication + assessed value stored on med_events and written into the entry). /debrief (instructor) renders a printable report: per-student summary, MAR with outcomes and verification, safety catches (scan alerts and blocks), monitor changes, provider thread, private observations, full timeline; print to PDF from the browser. Linked from Session setup and the Evidence timeline.


Checkpoint 8 (2026-10-14): head-to-toe / focused assessment documentation. Assessment tab on the chart: nine body systems, WDL tap or free-text findings per system, priority systems from the packet (neuro, cardiac, respiratory, pain) marked; focused reassessment shows priority systems first and links to the previous assessment. Server stores an append-only assessments row (systems JSON + monitor snapshot) and writes an ASSESSMENT_RECORDED entry with the per-system summary and the monitor values at the time. Instructor snapshot and debrief report include assessments. Verbal content is not captured; the record is what the student documented.


Checkpoint 9 (2026-10-14): instructor event injection. scenario.events (six scripted events from the packet: first ECG, chest pain episode, troponin/potassium results, hypotension after NTG, second ECG with SVT/V-tach, improving) each with a student-visible result, an instructor-only cue (stripped from student responses), and optional monitor vitals with a trend. POST /api/events/release (instructor) writes an EVENT_RELEASED entry and applies the vitals in the same transaction. Students see released events in an Updates panel on the chart and on the timeline; the instructor releases from a Scenario events panel on the Monitor page with elapsed time and suggested minutes. Automatic timed release remains R2 per the handoff.


Checkpoint 10 (2026-10-14): pilot MVP scope lock and UI pass. Faculty direction: no manual data entry; the kit teaches clinical judgement through observation of the room monitor, chart review, and medication administration with barcode verification, hold parameters and PRN judgement, driven by instructor-released scenario events. Removed from the UI (server endpoints retained, unrouted): nursing notes, student vitals documentation, assessment form, provider messaging. Student phone app: two destinations, Chart (read-only cards: Updates, SBAR, summary, labs, orders; persistent patient banner with live monitor line) and Meds (card list, scan-first Give). Instructor: Monitor and events, Patient chart (with facilitator pack and session panel), eMAR (policy, sim-day orders, physical barcodes), Evidence timeline (filter chips, debrief/export), Session. Phone layout is a scrolling column with a static bottom bar; 15px base type, 44px targets. Future (per faculty): AI patient voice for verbal assessment on a connected station, decision-impacted outcome variations, tagging actions to clinical judgement model domains.


Checkpoint 11 (2026-10-14): design cleanup and choice-based provider communication. Visual system: light surface, white cards with status colour bars, section labels, step indicator and segmented outcome control in the Give flow, compact page headings, patient banner as identity plus allergy and live-vitals chips, instructor manual vitals collapsed behind Adjust vitals manually with presets and scenario events first. Provider calls are RPG-style choices (no typing): scenario.providerScript lists situations, recommendations and provider replies; POST /api/provider builds the SBAR text (situation, background with live monitor values, recommendation) and POST /api/provider/reply (instructor) answers; free-text PROVIDER_* entries are rejected. Both roles have a Provider destination again.


Roadmap note (faculty, 2026-10-14): the room display is the natural home for the virtual patient. Next: a talking avatar on the display, video-call style, driven by the scenario state and an AI patient voice for verbal assessment. Later: a large touch display with a full-body interactive digital patient (the nursing-scenario counterpart of digital-cadaver anatomy tables), with touch regions for assessment and the monitor embedded. Both are new views over the same Pi scenario state and evidence log; the kiosk /display page is the seam to extend.


Checkpoint 12 (2026-10-14): Epic-inspired MAR and Active Orders. MAR (Rover/Hyperspace conventions): Identify the patient card at the top (one wristband scan opens a 10-minute med pass; each Give then needs only the label), medications grouped by time window with glyphs (Overdue, Due now, Upcoming, PRN, Continuous, Completed), next-due computed from last administration and interval, tap a medication title for order detail (source, indication, hold, last given, next due). Active Orders activity: categories Medications / Labs / Diagnostics / Nursing / Protocols; standing orders from the scenario plus dynamic orders; a provider reply can place new orders and activate medications (morphine, heparin) so the MAR changes as a consequence of the call; new orders carry a red dot on the nav and must be acknowledged (ORDER_PLACED / ORDER_ACKNOWLEDGED in evidence). Trending vitals now display whole numbers except temperature.

North star (faculty, 2026-10-14): the scenario as a never-ending set of NGN bow-tie items: cues (monitor, labs, released results, patient statements) -> problem -> actions -> outcomes, scored on cue recognition, prioritization and sequence given the current presentation. Epic Brain / Worklist is the target interface: one timeline of everything in the visit (due meds, reassessments after interventions, labs to draw, new result flags, procedures, calls) where the student taps an action as done and the instructor can confirm or flag it; that log is the clinical-judgement scoring mechanism and the hook for automated consequences. This is the next build.


Checkpoint 13 (2026-10-14): the scans are the documentation. When the wristband and the label both verify by camera and no alert is open, the administration is documented automatically (PRN indication taken from the order; no extra tap). The confirm step appears only when a decision is needed: an alert to acknowledge or hold, a hold/refusal, or a manual entry. The result panel states the five rights verified by scan.


Checkpoint 14 (2026-10-14): Worklist (the Brain). One timeline per visit, generated server-side (idempotent sync on every snapshot): scenario nursing tasks with triggers (at minutes from start, N minutes after a medication is first given, N minutes after a scenario event is released), review-new-result tasks for every released event, medication tasks from the MAR windows, and acknowledge tasks for new orders. Buckets: Overdue (>15 min), Now, Next hour, Later; Completed list with review state. Student taps Done (TASK_DONE entry carries lateness and the monitor values at the time); instructor Confirm or Flag (TASK_CONFIRMED / TASK_FLAGGED). Medication tasks complete through the MAR scan flow; order tasks through acknowledgement. Worklist is now the student home page. This log is the substrate for clinical-judgement scoring and automated consequences. Next: assessment and talk-to-patient components.


Checkpoint 15 (2026-10-14): verbal patient interaction. Patient page: hold-to-talk with the browser speech recognizer; POST /api/patient/ask logs PATIENT_ASKED (with the cue gathered) and PATIENT_SAID; the phone and the room display speak the reply (speechSynthesis) and the display captions the last exchange via /api/display. Two brains behind one endpoint: scripted (server/scenario.js patientVoice: persona, 29 keyword intents with phase-specific answers, including the sildenafil disclosure that contraindicates nitroglycerin) and AI (server/patientBrain.js: Claude Opus 5.5 via the Anthropic SDK, low effort, server-side fallbacks, cached system prompt built from scenario, phase, live vitals expressed as sensations, meds given, recent events and the last 12 exchanges; never breaks character; falls back to the script on refusal or error). Credential via ANTHROPIC_API_KEY or an ant auth profile; AI_PATIENT=off forces the script. Headless tests cover the scripted path; the AI path was not exercised in CI (no credential in the build shell).


Checkpoint 16 (2026-10-14, overnight): objective assessment by voice. scenario.exam lists 13 exam actions (lungs, heart, pulses, capillary refill, skin, edema, neuro orientation and grips, pupils, abdomen, chest wall, IV site, respiratory effort, PQRST pain) with keyword triggers, the patient's in-character response and the objective finding per phase. When the student verbalizes an exam, /api/patient/ask returns the patient reply plus the finding; the Pi logs EXAM_FINDING (system, phase) linked to the question; the room display shows an Assessment banner for 30 s and plays synthesized heart, breath (with crackles when the finding has them) or bowel sounds at the monitor rate (src/sounds.js, WebAudio, no media files). With the AI brain on, Claude plays the patient being examined while the finding stays deterministic from the scenario. The Worklist focused-assessment task completes itself once neuro, cardiac and respiratory findings have been gathered.

Student app: Worklist, Chart, MAR, Orders, Provider. Instructor: Monitor and events, Worklist, Patient chart, eMAR, Orders, Provider, Evidence timeline, Session.
