# Barcode medication verification + eMAR: MVP build plan

**Status 2026-10-14 (later): scan-first enforcement and physical-barcode registration added** (see design.md checkpoint 5). **S1-S5 built** (eMAR tab, verification dialog with blocked attempts, /labels page, phone camera scanning via ZXing with HTTPS from the installer, hold-rule flag from the live monitor). Decisions taken: phone cameras, no external scanner; all packet medications with sim-day meds selectable at setup; wall-clock due times from session start.

Goal: a student scans (or enters) the patient wristband and the medication label, the app checks both against the scenario's eMAR, and the administration (or the block, hold, or refusal) is written to the evidence timeline with who, when, and how it was verified. Manual entry is allowed but always logged as manual, never as a scan.

## Key finding: the camera is the hard part, not the barcode
Phone browsers only expose the camera over HTTPS. The Pi serves plain HTTP today, and a self-signed certificate must be trusted once on every student phone (iOS: install profile, then enable in Certificate Trust Settings; Android: install CA). That is doable but is the single biggest cost. A USB or Bluetooth "keyboard-wedge" barcode scanner (about $25-40) types the code into a text field, needs no HTTPS or camera permission, and works offline with the same code path as manual entry. The plan below builds the text-field path first so it works today on any device, then adds the camera on top.

## Build steps (each one is shippable on its own)
| Step | What | Effort |
|------|------|--------|
| S1 eMAR data + view | Scenario gains `medications[]` (name, dose, route, frequency, scheduled/PRN, hold rule, barcode value) from the Carl Shapiro orders, plus `patient.wristband`. New eMAR tab on the chart: due / given / held / refused with actor and time. Server: append-only `med_events` table; `POST /api/meds`. Evidence actions MED_GIVEN, MED_HELD, MED_REFUSED, MED_BLOCKED. | half day |
| S2 Verification flow | "Give medication" dialog: (1) patient ID, scan or type the wristband; (2) medication, scan or type the label; server checks both codes; wrong patient or wrong med is **blocked and logged** (valuable for debrief); five-rights checklist shown; confirm. `verification` recorded as `manual` or `scan`. Works immediately with typing or a wedge scanner. | half day |
| S3 Printable labels | `/labels` page renders the wristband and one label per medication as Code 128 SVG (small bundled encoder, no external assets). Instructor prints on paper or Avery labels and tapes them to the sim meds. | half day |
| S4 Camera scanning | HTTPS on the Pi (self-signed cert generated by the installer, trust instructions for iOS/Android in pi-deploy.md), `BarcodeDetector` with a bundled ZXing fallback, "Scan" button in the dialog that fills the same field; `verification: camera`. | 1 day + per-device trust testing |
| S5 Monitor tie-in | Hold rules reference live monitor values (e.g., "hold nitroglycerin for SBP <100"): the server attaches the SBP at the moment of administration to the evidence entry and flags a hold-rule conflict. Does not block; faculty decide in debrief. | half day |

S1-S3 give a working, offline, evidence-generating med pass in about two days. S4 adds camera-on-phone.

## Decisions needed before S1
1. Pilot scanning path: camera on BYOD phones (needs the certificate trust step) or one wedge scanner on a shared device. Recommendation for the first pilot: wedge scanner or typing, with camera added once the Pi is in the lab.
2. eMAR contents: all medications in the packet's orders by default, with the five "to be assigned day of SIM" meds marked assignable by the instructor at session setup.
3. "Due" times: wall clock from session start for now (e.g., scheduled meds due at +0 min and +60 min); instructor can mark anything due early. A scenario clock comes with event injection later.

## Not in this MVP
Drug library or interaction checking, allergy cross-check beyond the packet's listed allergy, dose calculation, IV pump programming, automated grading.
